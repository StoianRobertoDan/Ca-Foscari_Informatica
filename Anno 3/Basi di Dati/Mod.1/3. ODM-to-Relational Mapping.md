ODM is usually used for the conceptual modeling and then is translated in more practical terms into relational data modelling. This is done through a set of steps to avoid bad design:
- **Step 1**. Representation of 1: N and 1:1 associations:
	- ![[Pasted image 20250815020006.png]]
- **Step 2**. Representation of N: N associations:
	- ![[Pasted image 20250815020738.png]]
- **Step 3**. Representation of class hierarchies:
	- We assume that:
		- The subclasses are disjoint.
		- Class attributes are not redefined in subclasses.
		- ![[Pasted image 20250815020943.png]]
	- Options:
		- A **single relation** with the attributes of the class and subclasses and a special attribute "*discriminatory*" to track to which subclass a tuple belong.
			- ![[Pasted image 20250815022603.png]]
		- **Vertical partitioning**: a relation for the class and a relation for each subclass.
			- ![[Pasted image 20250815023129.png]]
		- **Horizontal partitioning**: a relation for the class and a relation for each subclass which include the class attributes too. 
			- If the subclasses are a disjoint cover, the class A is not defined because it would be empty in this representation.
			- ![[Pasted image 20250815023627.png]]
- **Step 4**. Define the primary key for each relation representing a class of the conceptual schema.
	- For each relation representing a subclass, the primary key is that selected for a superclass.
- **Step 5**. Representation of multi-valued attributes by having a dedicated relation.
- **Step 6**. Representation of composite attributes by replacing the record with its fields.
