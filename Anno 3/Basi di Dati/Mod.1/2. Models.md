Symbolic Model:
- Definition:
	- Is a subjective formal **representation** of ideas and knowledge about some aspects of the real world (**domain of discourse**), designed to serve an explicit purpose.
- Fundamental aspects from the definition:
	- A model is a representation of only some aspects of the real world, the one needed to serve a purpose of some kind.
	- The representation is given by a formal language.
	- The model is the result of an interpretation based on the knowledge possessed by the designer about that portion of the real world.
- The reality to be modeled is generally considered with respect to:
	- Concrete knowledge (structure):
		- **Entities**:
			- An entity is anything for which certain facts should be recorded, independently of the existence.
		- **Property**:
			- A property is a fact about an entity which is not meaningful in itself, but only because it describes an entity of interest.
		- **Type**:
			- A type is the list of information (properties and characteristics) that is shared by a group of entities.
				- (Entities with the same properties are said to have the same type).
		- **Collection/Entity set**: 
			- A collection or entity set is a set composed by all the entities with the same type.
			- A collection is subject to change, entities can be added or removed.
		- **Relationship**:
			- A relationship is a fact which correlates independent entities.
			- A collection of similar relationships is called relationship set.
	- Abstract knowledge (constrains):
		- Property constrains/classification:
			- **Atomicity**:
				- An *atomic property* can't be decomposed.
				- A *structured property* can be decomposed in multiple smaller values/properties.
			- **Multiplicity**:
				- A *single property* accepts just one value per entity.
				- A *multiple property* accepts more than one value per entity.
			- **Totality**:
				- A *total property* is mandatory for every entity.
				- A *partial property* is optional for each entity. 
		- Relationship/Structural constrains:
			- **Multiplicity**:
				- A *univocal relationship* is when an entity of type X can be correlated with just one entity of type Y.
				- A *multivocal relationship* is when an entity of type X can be correlated with multiple entities of type Y.
			- **Cardinality**:
				- The cardinality defines the multiplicity from one way and the other:
					- *One to one* (1:1):
						- The relationship is univocal both ways.
					- *One to many* (1:N) & *many to one* (N:1):
						- The relationship is univocal in one direction and multivocal in the other direction.
					- *Many to many* (N:N):
						- The relationship is multivocal both ways.
			- **Participation**:
				- A *total relationship* on X is when at least one entity of Y needs to be correlated to one in X.
				- A *partial relationship* is when there is formal need.
	- Procedural knowledge (behavior in changes).
	- Dynamics concerns (changes through events).
	- Communication (information exchanges).

Object Data Model (ODM):
- **Object**:
	- An object is the computer representation of certain facts about an entity of the observed world.
	- An object is a software entity with:
		- *State* (instance variables).
		- *Methods* (local operations).
			- *Messages* are used to comunicate operations.
		- Attributes (set of variables).
	- Objects have a unique identity (Object Identifier, OID) that persists over time and changes.
- **Object type**:
	- An object is an instance of a *type* defined with a *generative type constructor*.
	- An object type defines the state fields and the implementation of methods of it's possible instances.
- **Class**:
	- A mechanism of collection of objects is used to model databases:
	- A *class* is a modifiable sequence of objects with the same type. 
	- Assumption for use:
		- The only object types modeled are also element of a class.
		- The object type name is also the class name.
- **Relationship**:
	- Type of relationship:
		- Simple relationship.
		- Relationship with attributes (a class can be used in this case).
		- Recursive relationship.
- **Inheritance**:
	- Inheritance is a mechanism which allows something to be defined by describing how it differs (adding or modifying) from a previously defined one.
	- **Sub-typing**:
		- Is a relation between types.
		- Is asymmetric, reflexive and transitive.
		- In a sub-type definition, a property of a super-type can be redefined (overriding) and the object is given in the most specialized type to which the object belongs (late binding).
	- When inheritance is *strict*:
		- Properties can be redefined only by *specializing* their type.
		- A value of the sub-type can be used in all context where an element of the super-type is expected (context inheritance).
	- Class hierarchy:
		- This is an asymmetric, reflexive and transitive relation on the set of classes, such as that if $C_{1}$ SubsetOf $C_{2}$, then $C_{1}$ is a subclass of $C_{2}$:
			- The type of the elements of $C_{1}$ are a sub-type of the type of the elements of $C_{2}$ (intensional constraint).
			- The elements od $C_{1}$ are a subset of the elements of $C_{2}$ (extensional constraint) and $C_{1}$ inherits the relationships defined on $C_{2}$.
		- A subclass can be defined from a single superclass (simple inheritance) of from several superclasses (multiple inheritance).
		- **Constraints**:
			- *Overlap*:
				- Non overlapping (*disjoint*) subclasses are not allowed to contain the same element.
					- Visual representation: small back circle.
				- Overlapping subclasses are allowed to contain same elements.
			- *Covering*:
				- A cover is when the objects in the subclasses collectively include all the elements in the superclass.
					- Visual representation: double line on the arrow.
			- A disjoint cover is called a *generalization*.

Relational Data Model:
- **Relational schema**:
	- A relational schema $R:\{T\}$ is a pair composed by a name $R$ and a relation type $\{T\}$:
		- *Integers*, *floats*, *booleans* and *strings* are *primitive* types.
		- If $T_{1}, ... ,T_{n}$ are primitive types and $A_{1}, ... ,A_{n}$ are distinct attribute names, then $(A_{1}:T_{1}, ... ,A_{n}:T_{n})$ is a *tuple type of degree n*.
			- The order is not important.
			- Tuples with the same degree and set of pairs are equal.
		- If $T$ is a *tuple type* then $\{T\}$ is a *relation type*.
			- Relation types are equal if they have the same tuple type.
- **Tuple**:
	- A *tuple* $(A_{1}:=V_{1}, ... ,A_{n}:=V_{n})$ of type $(A_{1}:T_{1}, ... ,A_{n}:T_{n})$ is a set of pairs $(A_{i},V_{i})$ with $V_{i}$ of type $T_{i}$.
	- Tuples with the same type and same set of pairs are equal.
	- A *relation* is a finite set of tuples
		- Relations with the same type and set of tuples are equal.
	- The extension of a relational database is a collection of the extensions of its relational schemas.
- **Key**:
	- A *key* is a minimal subset of attributes whose values identify a tuple.
		- Every tuple have a specific key and all tuples have a different key. No tuple can have the same key as another tuple.
	- The *primary key* is a key chosen to be used in the database, usually the key with the least number of attributes.
	- An *external key* is an attribute of a relational schema that directly refers to the primary key of another relational schema.
